# clearmind-ui

Інтерфейс ревізії Telegram-підписок ClearMind. Показує стійке дублювання між каналами, на які підписаний користувач, і подає до кожної рекомендації пакет доказів, за яким рішення можна перевірити, а не прийняти на віру.

Відписку виконує людина. Система не діє в Telegram від імені користувача — вона лише пояснює, що знайшла.

Це єдина поверхня стека, доступна ззовні кластера: у розгортанні застосунок — статичний бандл, який віддає nginx, а виклики до API проксуються на `api-gateway`.

## Стек

| Що | Чим |
|---|---|
| Каркас | React 18, React Router 7 |
| Збірка | Vite 6, TypeScript 5 |
| Оформлення | Tailwind 4, дизайн-система Nocturne (`src/styles/nocturne.css`) |
| Виклики API | Connect-Web поверх згенерованих контрактів `clearmind.v1` |
| Тести | Vitest + Testing Library, Playwright + axe |
| Образ | багатоетапна збірка, у кінцевому образі — лише nginx і бандл |

## Ролі й екрани

Роль приходить від сервісу ідентифікації разом із сесією; у сховищі її немає, тож підмінити її на клієнті нічим. Маршрути розділені за ролями: те, що бачить `admin`, недосяжне для `user`, і навпаки. Закрита для ролі адреса віддає сторінку «не знайдено», а не порожній екран.

| Маршрут | Роль | Що робить |
|---|---|---|
| `/login` | — | вхід паролем або за ID-токеном Google; доступні способи приходять із контракту |
| `/import` | `user` | імпорт підписок: файл експорту, перевірка розпізнаних діалогів, обробка, підсумок |
| `/review` | `user` | ревізія підписок: знайдене дублювання по снапшоту |
| `/recommendations` | обидві | перелік рекомендацій із розкриттям пакета доказів |
| `/account` | обидві | акаунт і підписки, створення снапшоту |
| `/channels/:id` | обидві | картка каналу: характеристики, схожі канали, історія додавання |
| `/catalog` | `admin` | каталог каналів із пошуком |
| `/pairs` | `admin` | пари каналів зі знайденим дублюванням |
| `/admin/recommendations` | `admin` | рекомендації в розрізі снапшоту |
| `/settings` | `admin` | параметри аналізу |
| `/runs` | `admin` | історія запусків збору й аналізу |
| `/events` | `admin` | журнал доданих каналів |

Кореневий маршрут веде на `/catalog` для `admin` і на `/review` для `user`.

### Імпорт і запуск

Підтвердження на кроці перевірки заморожує снапшот **і запускає** для нього збір, за яким іде аналіз. Крок обробки — вікно в стан цих запусків: запуск живе на сервері, тож закрита вкладка нічого не зупиняє, а відкритий заново екран знаходить незавершений запуск найновішого снапшоту й повертається до нього. Нічого про запуск на клієнті не зберігається: питання «чи щось іде» має відповідь у контракті.

Вікно збору на запуск **не передається**: незаповнене значення означає вікно з параметрів аналізу, і розв'язує його `api-gateway`. Читати ті параметри дозволено лише ролі `admin`, а екран імпорту існує для ролі `user`.

Частка виконання показується лише там, де знаменник справді існує. Скільки публікацій канал віддасть за вікно, до читання його історії не знає ніхто, тож рядок каналу має лічильник зібраного й підпис останньої дії, а не смугу з вигаданим відсотком; загальна частка збору спирається на канали. Підпис останньої дії складається тут, а не приходить із контракту — з сервера йдуть лише факти, яких клієнту не вивести самому: час перевикористаного збору й залишок очікування ліміту.

### Пакет доказів

Сигнали подаються **роздільно** — лексичний збіг, спільні посилання й домени, пересилання, часовий профіль — а не одним агрегованим числом. Поруч показані частка унікального контенту, оцінка ризику втрати та приклади збігів із посиланням на конкретні публікації обох каналів.

### Рішення користувача

Дії — «підтвердити», «відхилити», «відкласти». Рішення зберігається у ClearMind; **жодної дії в Telegram від імені користувача система не виконує**, відписка робиться вручну.

## Адреса API

Адреса `api-gateway` **не зашита в бандл**. Клієнт звертається на той самий origin, а маршрутизацію робить nginx.

| Змінна | Обов'язкова | За замовчуванням | Призначення |
|---|---|---|---|
| `API_GATEWAY_URL` | ні | `http://api-gateway` | адреса, на яку nginx проксує API |

Змінна читається не застосунком, а nginx: `envsubst` підставляє її у шаблон конфігурації під час старту контейнера.

## Правила проксування nginx

| Маршрут | Куди йде |
|---|---|
| `/clearmind.v1.<Сервіс>/<Метод>` | `${API_GATEWAY_URL}` — Connect-виклики |
| `/api/...` | `${API_GATEWAY_URL}` |
| `/live`, `/ready` | локальна відповідь `200` |
| решта | статика; невідомий шлях віддає `index.html` |

Проксується лише публічна поверхня `clearmind.v1` — міжсервісні контракти ззовні недосяжні. Буферизація на Connect-маршрутах вимкнена, щоб прогрес запуску був видно одразу.

Порт контейнера — `8080`, непривілейований. Процес виконується не від імені `root`.

## Контракти

Клієнт до API не пишеться руками: `contracts/` — згенерований із `proto` код, підключений як локальна залежність `@clearmind/contracts`. Він комітиться і руками не редагується; зміна взаємодії починається зі зміни контракту.

Згенеровано **лише** з `proto/clearmind/v1`, тож у бандлі немає міжсервісної поверхні — це перевіряється складом зібраного бандла.

Оскільки згенерований код лежить в окремому пакеті, його імпорти рантайму (`@bufbuild/protobuf`, `@connectrpc/connect`) резолвяться явними псевдонімами у `vite.config.ts` і `tsconfig.json`. Без цього типи методів деградували б до `any`.

## Структура репозиторію

```
src/screens/      екран на маршрут
src/components/   спільні блоки: оболонка, стани, пакет доказів, картки запусків
src/hooks/        запуск збору й аналізу
src/lib/          сесія, клієнти Connect, помилки, форматування
src/styles/       дизайн-система та розкладка застосунку
tests/            компонентні тести (Vitest + Testing Library)
e2e/              наскрізні тести (Playwright) зі сценарними відповідями контракту
contracts/        згенерований клієнт clearmind.v1
```

## Розробка

```bash
npm install
npm run dev      # Vite на :5173, проксує Connect-маршрути на localhost:8080
```

У розробці роль nginx виконує проксі Vite, тож `api-gateway` достатньо запустити локально на `:8080`.

### Збірка й перевірки

```bash
npm run build         # tsc --noEmit + vite build
npm run lint          # tsc --noEmit
npm test              # vitest
npx playwright test   # e2e проти зібраного бандла
```

Компонентні тести покривають екрани ревізії, імпорту, каталогу, параметрів, запусків і рекомендацій: розкриття доказів, роздільні сигнали, приклади збігів, три дії рішення й відновлення сесії.

E2E ганяються проти зібраного застосунку зі сценарними відповідями контракту, а не проти кластера: стани, на яких екран колись брехав — провалений збір, частковий збір, аналіз без результату проти аналізу, що не виконувався, — у живому стеку відтворюються недетерміновано. Окремо перевіряються інваріанти екранів: доступність (axe), єдиний заголовок першого рівня, видимий фокус із клавіатури, і те, що токен сесії не потрапляє в сторінку.
